Current architecture · July 2026

Pumice is a fail-closed, service-aware task runner.

Each Git worktree has one short-lived daemon that owns service locks, child processes, dependency state, ports, and invocation leases. CLI processes are clients—not process owners.

System map

User edge
npm launcher

Selects the platform binary and forwards terminal signals and stdio.

pum run <task> clients

Load and validate configuration, derive the canonical worktree identity, then connect over a private Unix socket.

versioned JSON messages, streamed stdin/stdout/stderr, connection lease
Control plane
Worktree daemon

Single lock authority. Owns active invocations, service state, dependency propagation, configuration epoch, and managed ports.

Startup + lifetime locks

Filesystem flocks prevent concurrent daemon creation and competing authorities.

Service manager

Atomically reserves names across starting, healthy, and stopping states.

Dependency graph

Stops transitive dependents immediately when a required service exits.

one private lease pipe per command; daemon owns the write end
Process plane
Process supervisor

Watches the daemon lease, starts the shell command, reports its PID, and sweeps the process group.

Task, service, or health-check process group

Runs in the project root with daemon-managed port variables. A lost lease forces group termination.

Normal invocation flow

1

Discover

The CLI finds pumice.yaml, validates the graph, and resolves the canonical Git worktree.

2

Connect

It connects to the worktree socket. A startup flock serializes daemon creation when none exists.

3

Register

The socket becomes an invocation lease. EOF cancels the invocation and releases all references.

4

Acquire

Each service name is reserved before launch. Concurrent dependencies wait on the same readiness record.

5

Start + ready

The supervisor launches the process group. Health checks establish readiness only.

6

Release

References are removed on completion. Zero-reference services stop in dependent-first order.

Failure behavior

Failure Authoritative signal Immediate outcome
CLI is killed Unix socket EOF Invocation is cancelled, its references are released, and newly unreferenced services stop.
Service exits Supervisor/process Wait Transitive dependent services stop and all affected invocations fail. Health-check correctness is irrelevant.
Daemon is killed Kernel closes lease pipes and client sockets Supervisors kill their process groups; listening CLI processes receive EOF and exit.
Command leader exits Supervisor receives child completion The supervisor sweeps the remaining process group so ordinary descendants cannot become orphans.
Incompatible client connects IPC protocol mismatch The request is rejected without replacing or disturbing the active daemon.

Version and repository isolation

Different worktrees: different runtime hashes, sockets, ports, daemons, and service locks.
Same worktree: exactly one daemon authority, regardless of which npm installation launched it.
Compatible package versions: share the daemon according to protocolVersion, not npm semver.
Breaking changes: bump the protocol compatibility epoch; never create parallel version-specific daemons.
Package upgrade: active work continues on the existing daemon; after idle exit, the next command launches the new binary.
Idle lifetime: the daemon exits 250 ms after its last connection and service disappear.

Core invariants

One authority

No JSON registry, PID file, port, or health check acts as the service lock.

Fail closed

Losing coordination terminates work rather than leaving ambiguous background state.

Readiness ≠ liveness

Health checks gate dependents. Operating-system exit events establish process death.

Reference ownership

A service remains alive only while at least one connected invocation requires it.

Dependency ordering

Dependents start after requirements are ready and stop before those requirements.

Configuration epoch

Graph changes are accepted only when no active command or service uses the previous configuration.

Known boundaries

Unix foreground-process model. Pumice supports macOS and Linux and contains normal descendants with process groups. A command that deliberately escapes with setsid can evade portable process-group containment; services should therefore run in the foreground. Absolute containment of hostile daemonization would require platform-specific facilities such as Linux cgroups or an operating-system service manager.

Managed port selection still has the standard bind-and-release race before an application claims its assigned port. This does not affect locking because ports are values, never lock authorities.
